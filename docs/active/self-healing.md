# 平台内自愈与问题收件箱

> 更新：2026-11-26。本文记录平台内自愈的已实现范围、权限边界和验证证据；不是对外承诺。

## 目标

平台内错误先进入统一问题总线，由智能体做只读诊断和结构化计划；能自动处理的 R0/R1
直接执行并验证，需要授权的 R2/R3 等管理员确认，解决不了的保留证据并给用户可执行的
协助步骤。全过程只在千枢平台内动作，不外溢到主机、云侧写或外部通知。

## 统一问题总线

| 项 | 实现 |
|---|---|
| 数据表 | `issue_cases`、`issue_plans`、`issue_events`；活动指纹部分唯一索引防并发重复 |
| 来源 | 接入（onboarding）、云同步（cloud_sync）、严重告警自动诊断（alert）、API 5xx、后台任务（job）、智能体工具/工作流（agent）、copilotd 生命周期 |
| 聚合 | 同指纹累加次数并只发一条站内信；单来源每分钟超阈值合并为“错误风暴”；恢复后同指纹复发升级人工 |
| 状态 | `open` → `diagnosing` → `awaiting_approval` / `awaiting_user` / `repairing` → `verifying` → `recovered`，另有 `recurring`、`manual_required`、`ignored` |
| 通知 | 只写站内信（`agent_issue`，管理员受众）；不接企微、钉钉、短信、电话 |
| 审计 | 计划授权/拒绝/过期、执行、重启委托、验证、失败、回滚、熔断重置均有固定动作名 |

接入失败不再直接阻断后续账号和能力；上报使用独立短事务，上报失败只记日志，不能反向
影响主业务。同一资产失败只生成一张问题单，不在 onboarding 与 cloud_sync 各建一张。

## 风险分级与执行

固定动作目录 `backend/app/services/self_heal/catalog.py` 决定风险级别；模型自报的风险
一律忽略。模型只能选择目录内 recipe 和结构化参数，不能生成命令、SQL、PromQL 或 URL。

| 级别 | 动作 | 执行条件 |
|---|---|---|
| R0 | 重试接入能力、刷新云资产、重新发现日志、回读指标、重采账单日、只读连通探测、重置本问题运行标记 | `auto_r0` 模式可自动执行；`observe`/`assist` 只记录或需人工触发 |
| R1 | 仅在该账号没有任何默认规则时补种默认告警规则 | 同 R0，不覆盖用户已有规则 |
| R2 | 重启千枢后端（经本机 copilotd token 通道）、重载平台内设置、修正平台内账号 endpoint | 管理员按完整计划哈希授权后执行，永不自动 |
| R3 | 通过既有 `code_mod`/`change_gate` 修改允许路径下的平台代码 | 管理员查看 diff 和完整计划哈希后授权；验证失败自动回滚 |
| R4 | 任意命令/SQL/PromQL、主机重启、系统参数、平台外资源、外部云写、外部通知、删库、改权限或自愈核心 | 目录中不存在，出现即拒绝 |

执行约束：

- 计划使用规范化 JSON 的 SHA-256 作为不可变哈希，绑定问题单与计划版本；授权和执行时
  都重新校验，计划内容变化必须重新授权。
- 同一问题单同一时间只允许一个执行；计划有过期时间，过期必须重新生成。
- R0/R1 自动失败按冷却时间重试，达到 `max_attempts` 或连续失败熔断后停止；恢复后复发
  不再自动执行。
- 重启仅委托本机 copilotd 的 `/restart`，不执行 `systemctl`、不重启服务器、不改系统参数。
- 代码修改只允许 `code_mod` 白名单路径，且 `self_heal`、copilot 管道、通知、审计、问题
  API、copilotd 自身全部在拒绝清单内，LLM 不能扩大自己的权限或绕过审批。
- 不删除千枢数据库数据；R0 的“重置本问题状态”只清理运行中标记。

## 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `SELF_HEAL_ENABLED` | `true` | 总开关；关闭时只保留表结构，不建问题单、不自动维护 |
| `SELF_HEAL_MODE` | `observe` | `observe` 只记录；`assist` 允许诊断但 R0 也需人工触发；`auto_r0` 允许 R0/R1 自动执行 |
| `SELF_HEAL_LLM_ENABLED` | `false` | 是否允许模型参与诊断；关闭时仍记录问题并给确定性处理建议 |
| `SELF_HEAL_KILL_SWITCH` | `false` | 立即冻结上报、诊断、执行、启动收口和后台维护写操作 |
| `SELF_HEAL_MAX_ATTEMPTS` / `SELF_HEAL_MAX_PLANS_PER_DAY` | 3 / 30 | 自动修复与计划预算 |
| `SELF_HEAL_STORM_PER_MIN` / `SELF_HEAL_RECURRENCE_HOURS` | 20 / 24 | 风暴聚合与复发窗口 |
| `SELF_HEAL_PLAN_TTL_MIN` / `SELF_HEAL_BREAKER_FAILS` | 1440 / 5 | 计划有效期与熔断阈值 |

R2/R3 的授权入口是“智能体 → 问题收件箱”：管理员看到完整计划哈希、风险级别和代码 diff
后确认；服务端按计划哈希再次校验，页面或模型都不能绕过。

## 验证证据

隔离验证（一次性 PostgreSQL 16、临时后端与 Vite、外部动作全部替身）：

- 自愈专项 7 个套件共 263 项通过：服务 23、计划 41、执行 43、接口 47、来源 34、
  硬化 25、回放 50。
- 接入相关回归：onboarding 26、云接入 67、厂商能力 35、节奏 7、拓扑 15、SLS 77，
  全部通过。
- 静态质量门：断链 0、绑定 37 文件、模型字段 0 问题、Vite 编译 0 失败、路由覆盖 0
  缺口、跳转目标 0 缺口、审计动作 0 未登记；结构指纹 0 项问题。
- 前端生产构建通过。

未验证或明确不做：

- 未在真实云账号上执行 R0/R1 修复动作，未真实重启千枢后端，未真实应用 R3 代码补丁；
  这些路径由 mock 与执行器测试覆盖，不等于生产环境演练。
- 不执行云侧写、主机重启/关机、系统参数变更、平台外资源写、外部通知或数据库删除。
- 5xx 上报按“方法+路径”每分钟限流；同一路径持续故障只保留一张问题单。
